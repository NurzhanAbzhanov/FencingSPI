# Coaches Poll Migration Design

**Status:** Approved design
**Date:** 2026-08-11
**Source application:** `usfca-coaches-poll-main (1).zip`

## Context

The SPI platform currently contains a prototype coaches poll inside a Vite React application. The supplied USFCA coaches poll is a separate Next.js application with the desired poll categories, ballot workflow, poll administration, participation tracking, results, and school-logo support.

The supplied poll must replace the prototype poll, while the existing SPI platform remains responsible for programs, seasons, match results, power ratings, and Team and Squad SPI calculations. The migration must not introduce a second database model or require administrators to upload SPI data manually.

## Goals

- Replace the existing poll pages and behavior with the supplied poll experience and rules.
- Keep the existing Vite application, static Vercel deployment, Supabase authentication, and normalized fencing data model.
- Populate poll reference data from calculated Team and Squad SPI and current match results.
- Preserve schools, programs, seasons, administrators, coaches, permissions, matches, SPI results, and power-rating overrides.
- Use the supplied school-logo mappings throughout both poll and SPI pages, with an initials fallback.
- Enforce voting, visibility, and poll-state rules in Supabase as well as in the browser.

## Non-Goals

- Migrating the platform to Next.js.
- Running the coaches poll as a second application.
- Importing or calculating historical SPI.
- Importing the historical match workbook.
- Providing a manual poll SPI upload page.
- Changing the SPI or power-rating formulas.

## Architecture

The existing Vite application remains the host application. Supplied Next.js pages are treated as the product and interaction reference, then adapted into framework-neutral React components that follow the current application's routing, authentication, and styling boundaries.

The platform has four layers:

1. **Presentation:** poll dashboard, ballot, results, public results, participation, coach management, and poll management pages.
2. **Repositories:** typed operations for loading poll state, candidates, ballots, snapshots, results, coaches, and participation.
3. **Domain logic:** category definitions, eligibility, Division III consistency, ballot validation, and standings calculation.
4. **Supabase:** authoritative records, transactional state changes, row-level security, and audit history.

No poll page reads static SPI fixtures. No component accesses Supabase directly. Components call repository functions and render explicit loading, empty, error, and success states.

## Existing Data Model

The migration retains these normalized tables:

- `seasons`
- `schools`
- `programs`
- `program_seasons`
- `matches`
- `spi_results`
- `power_rating_overrides`
- `profiles`
- `poll_periods`
- `ballot_definitions`
- `ballots`
- `ballot_rankings`
- `published_poll_results`
- existing audit records

The existing `profiles` table remains the source for administrator and voting permissions. Program eligibility continues to come from `program_seasons`, including season-specific division, conference, and region.

## Schema Additions

Add `poll_spi_snapshots` with one row per poll period, program, and weapon. Each row stores:

- poll period and program IDs
- gender and weapon
- SPI value and SPI rank
- calculated power rating when available
- division, conference, and region at capture time
- capture timestamp

The snapshot has a unique constraint on `(period_id, program_id, weapon)`. It is generated by the database when an administrator opens a poll and is never manually uploaded.

Add or align poll scheduling fields needed by the supplied workflow, including scheduled opening and closing timestamps. Add an archived marker to unsupported prototype ballot definitions when necessary. Existing prototype rows remain available for audit but replacement pages query only active, supported definitions for the selected period.

## Poll State Machine

Poll periods use these states:

- `draft`: editable by administrators and invisible to coaches
- `open`: ballots can be created and edited
- `closed`: ballots are immutable and visible to the committee
- `published`: aggregate results are public

An administrator-only database function opens a poll in one transaction:

1. Close any other effectively open poll.
2. Verify the period belongs to a valid season.
3. Verify calculated SPI exists for all eligible candidates.
4. Replace the period's draft snapshot with the latest calculated SPI and season metadata.
5. Create or validate the supported ballot definitions.
6. Mark the period open and write an audit record.

Ballot writes check both stored status and scheduled closing time in the database. A period whose closing time has passed is treated as closed even before an administrator finalizes it. Closing freezes ballots. Publishing calculates and stores final aggregate rows before exposing them publicly.

Only one poll period may be effectively open at a time.

## Categories And Ballot Rules

The supplied category configuration is authoritative:

| Category | Gender | Scope | Slots | Visible |
| --- | --- | --- | ---: | --- |
| Team | Men and Women | Overall | 15 | Yes |
| Team | Men and Women | Division III | 8 | Yes |
| Epee | Men and Women | Overall | 15 | Yes |
| Foil | Men and Women | Overall | 15 | Yes |
| Sabre | Men and Women | Overall | 15 | Yes |
| Epee, Foil, Sabre | Men and Women | Division III | 5 | No |

Every authorized coach completes every visible category. Coaches may vote for their own school.

Ballots begin as empty numbered slots. A coach selects one eligible program per slot. Submission requires every slot to be filled and every program to be unique. A submitted ballot remains editable until the poll closes.

Men's and Women's Team Division III ballots require the matching Team Overall ballot to be submitted first. Division III programs selected in Overall are copied into the first Division III slots in Overall rank order and locked. Supabase revalidates this relationship whenever the Division III ballot is saved.

## Poll Standings

Each rank receives reverse points: rank one receives the category slot count and the final rank receives one point. Standings sort by:

1. total points descending
2. first-place votes descending
3. canonical school name ascending for deterministic ordering

Ranks remain sequential after sorting. Exact equality does not create a shared rank, matching the supplied application's current behavior.

Aggregate standings are recalculated when a poll closes and stored when published. Published rows include points and first-place-vote counts. Individual ballots become visible to authenticated committee members after closing, while anonymous visitors can see only published aggregate results.

## Application Pages

### Poll Dashboard

Shows the active or most relevant poll, its closing time, category completion, editing state, and links to closed or published results. Hidden categories do not appear.

### Ballot Page

Uses the supplied numbered-slot and searchable combobox layout. It includes:

- category and poll context
- completion count
- locked Division III slots where applicable
- clear-editable action
- review and confirmation dialog
- submitted-ballot editing banner
- automatic closure detection

The adjacent SPI reference table reads only from `poll_spi_snapshots`. It displays rank, logo, school, division, conference, region, SPI, and power rating when available. Each school links to the existing current-season match-results page. Quick-rank actions fill the first empty editable slot.

The label and behavior for manually uploaded SPI are removed.

### Results

Authenticated results include category standings, points, first-place votes, participation, and individual ballots after closing. Public results show published aggregate standings only. Both support CSV download.

### Administration

Administrators can:

- schedule, open, close, and publish polls
- manage coach access and voting permission
- inspect completion by coach and category
- review aggregate and individual results

Opening a poll clearly reports snapshot validation failures instead of opening with partial reference data.

### SPI And School Pages

Team SPI, Squad SPI, poll tables, and school-result pages use one shared `SchoolLogo` component. It uses the supplied logo mappings and accepts the platform's canonical school names and known aliases. Image failures and unmapped schools render stable initials without changing row dimensions.

## Repository Interfaces

Poll components use focused repository operations such as:

- `loadPollDashboard`
- `loadBallot`
- `saveBallot`
- `loadPollSpiSnapshot`
- `loadPollResults`
- `loadIndividualBallots`
- `loadParticipation`
- `openPoll`
- `closePoll`
- `publishPoll`
- `saveCoachPermissions`

Repositories return domain types rather than raw Supabase join shapes. Supabase-specific row mapping remains inside repository modules.

## Authorization And Row-Level Security

- Administrators manage poll periods, coaches, definitions, snapshots, publishing, and audit records.
- Voting coaches read active definitions and snapshots and can create or update only their own ballots while the period is effectively open.
- Coaches cannot change submitted rankings after closing.
- Authenticated committee members can read individual ballots only after closing.
- Anonymous users can read schools, public reference data, published aggregate results, and approved match scores shown on school-result pages. They cannot access the match-entry interface, submission metadata, administrative match operations, or individual ballots.
- Match creation, editing, and deletion remain administrator-only.
- Database functions independently validate role, poll state, ballot size, uniqueness, candidate eligibility, and Division III consistency.

## Error Handling

- Opening is blocked when candidate SPI snapshots are incomplete.
- Saving rejects missing, duplicate, ineligible, or incorrectly sized rankings.
- Saving rechecks poll status and scheduled close time immediately before writing.
- Publishing is blocked unless the poll is closed and aggregate calculation succeeds.
- Repository failures produce actionable page-level messages and preserve the user's unsaved browser state.
- Missing SPI or match data produces an explicit empty state, never fabricated values.
- Logo failures fall back to initials.
- Administrative mutations create audit records with actor, action, target, and timestamp.

## Migration Strategy

1. Introduce the snapshot table, poll state functions, validation functions, and RLS policies.
2. Add repository and domain tests before changing routes.
3. Port shared poll components and the logo resolver.
4. Replace prototype poll routes page by page.
5. Add logos and poll result context to existing SPI pages.
6. Archive unsupported prototype definitions and exclude incompatible prototype ballots from official views.
7. Verify against local and configured Supabase environments.
8. Deploy database migrations before the Vercel frontend.

The migration preserves user accounts, permissions, and fencing data. Browser-local demo users and ballots are not imported as official records.

## Verification

### Unit Tests

- category metadata and visibility
- reverse-point scoring
- first-place-vote tiebreaks and deterministic final ordering
- gender, weapon, and Division III eligibility
- Division III auto-fill and locked-slot derivation
- logo mapping and fallback

### Repository And Database Tests

- snapshot creation and completeness checks
- one-open-poll enforcement
- ballot creation and editing while open
- write rejection after scheduled or manual close
- ballot size, uniqueness, and eligibility validation
- Division III prerequisite and consistency validation
- close and publish transitions
- administrator, coach, committee, and anonymous RLS behavior

### Component And Browser Tests

- dashboard completion states
- empty ballot and searchable selection
- quick-rank and duplicate prevention
- review, submit, edit, and resubmit
- Division III prerequisite and locked slots
- closed and published results
- CSV downloads
- desktop and mobile layouts for poll, admin, Team SPI, and Squad SPI pages

### Release Checks

- TypeScript build and production Vite build pass.
- Supabase migrations apply cleanly.
- No official page reads local demo poll storage.
- No poll page depends on static or manually uploaded SPI data.
- A post-deployment smoke test covers admin login, poll opening, coach voting, closing, publishing, public results, and school match links.

## Deferred Work

Historical match normalization and historical SPI calculation are intentionally deferred. They will require a separate specification once season-specific historical power ratings or published historical SPI values are available.
