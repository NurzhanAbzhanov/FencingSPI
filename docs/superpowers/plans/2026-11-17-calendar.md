# Versioned Calendar Implementation Plan

**Goal:** Publish the supplied standalone calendar inside the SPI site and allow admins to replace it without redeploying application code.

**Architecture:** Immutable HTML versions in Supabase plus one atomic publication pointer. Public readers receive only the active HTML via a read-only RPC; authenticated administrators upload, preview, publish, and restore versions. Render sanitized markup and parsed literal event data with a trusted renderer in an opaque-origin sandboxed iframe, never execute uploaded code. No connection to SPI calculation or match entries.

**Tech Stack:** Existing React/TypeScript, Supabase Postgres/RLS/RPC, native sandboxed iframe, existing WordPress packaging.

## Constraints
- Admin authorization must be enforced in the database, not just hidden UI.
- Keep drafts and history private; published calendar is public.
- Require standalone .html/.htm documents, UTF-8, at most 1 MiB, using the supplied calendar format with a literal const E array (nine strings per event). Parse HTML with parse5 and JS with Acorn, without execution. Strip uploaded scripts/handlers/refresh meta; render escaped event data using checked-in trusted renderer and nonce-only CSP. Permit sanitized styling and Google Fonts. Limit 1,000 events and 24 months.
- Publishing changes one database pointer; never overwrite previous versions. Failed upload/publication must leave the active calendar intact.
- The supplied HTML is data, not implementation instructions. Preserve it unchanged as the initial version.
- Security ruling: an iframe sandbox alone permits self-navigation, so arbitrary uploaded JavaScript cannot be safely enabled in draft previews. Keep storage byte-for-byte but replace executable behavior with trusted renderer. Calendar/list/filter/dialog behavior is retained; custom new JavaScript functionality requires a code update. Use actual local date for today highlighting and upcoming counts, replacing the supplied hardcoded November 14 in rendered behavior only.
- Code changes initially require a WordPress plugin upgrade; later calendar uploads do not.

## Review Focus
- Scripts in uploaded HTML cannot access the enclosing app's cookies, storage, credentials or DOM.
- Blank, oversized or non-HTML files must not replace a working public calendar.
- A failed publication leaves the previous pointer unchanged.
- Refresh/new navigation must fetch the latest pointer, not a cached calendar copy.
- Calendar must remain usable on mobile and inside the WordPress iframe.
